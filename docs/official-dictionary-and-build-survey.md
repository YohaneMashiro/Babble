# 官方字库与开源构建方案调研

核查日期：2026-10-26（Asia/Dubai）。本轮检查官方文档、上游源码、构建脚本和许可说明，未修改 Babble 运行库，也未导入新的官方原始数据。

2026-10-27 已推进到工具实现：官方快照的条件更新与差异报告、Chai 构建期试验及本机运行记录见[字库校对工作流](dictionary-review-workflow.md)。本文保留调研时的事实与统计，工具运行结果单独记录。

## 结论

官方已经提供成熟的字词库管理、挂接和安装版生成指导。社区也有成熟的 Rime 词典组织、格式转换、编译与更新流程。但“将已有码表编译成可用输入法”与“从字形生成完全符合官方规则、带逐字解释的数据库”是两类任务；本次未找到官方公开的后一类完整源码工程。

对于 Babble，最值得进一步验证的是 **汉字自动拆分系统 Chai**：它有笔画拓扑、字根识别和可配置拆分规则，明确考虑小鹤的相交限制。它是较完整的通用构建平台，尚不能称为现成、经过官方全库核验的小鹤配置。

## 官方怎样组织字库

1. **明确常规字集。** [官方入门](https://flypy.cc/help/#/xh)指定以《通用规范汉字表》的 8,105 字为主体；表外还可用 OK 拼字补充，官方说明其支持 GB 18030-2022。不能据此推断所有 Unicode 汉字都有常规四码。
2. **区分字、编码和词条数量。** [常见问题第九节](https://flypy.cc/help/#/wt)给出截至 10.26.8 的统计：单字编码约 1.38 万、单字全码 8,726 条、词编码约 5.92 万；这些含简码、多音或容错等重复，另补充表外 300 余字。8,726 条全码不能直接称为 8,726 个不同汉字。[更新日志](https://flypy.cc/win_record.html)已有 10.26.9，因此这里保留原统计版本，不将其称为最新条目数。
3. **按用途分词典。** [Windows 说明](https://flypy.cc/help/#/pc)列有首选、次选、表外、随心、用户、全码字词、拼字等分类。部分已有简码的字会让出全码位置，全码另存、在熟手设置下隐藏。因此，只检查主候选词典可能漏掉实际存在的完整编码。
4. **支持用户维护和编译。** [用户词库](https://flypy.cc/help/#/yh)使用 TXT 的词条与编码记录，支持导入、导出和批量词语编码，多音词需修正。[Android 说明](https://flypy.cc/help/#/sj)明确说明重载会把 TXT 生成 BIN。这是已有词库的编辑与编译，不等于从笔顺自动生成首末形。
5. **存在明文挂接资源。** [官方挂接指导](https://flypy.cc/help/#/gj)明确提供百度安卓版个性短语 INI，并指导转换成其他短语格式；还介绍 DDimegen、多多、小胖与 Rime，以及自行生成安装版。不能笼统地说官方所有码表都只有二进制。本轮未取得并逐包检查当前网盘安装包。

官方文档公开了规则和使用流程；在本次检查的文档及下载入口中，未发现完整官方字库的开放许可证或从底层字形到全库的可复现生成源码。[应用说明](https://flypy.cc/help/#/yy)也区分个人挂接与第三方内置方案。公开下载、程序开源和具体字库的再分发许可须分别核对，不能相互替代。

以上描述的是公开资料中可观察到的组织方式；官方内部是否还有未公开的自动生成或校对工具，本轮没有证据作判断。

cubercsl 的两个转换脚本已分别声明 WTFPL；旧调查仅凭根目录没有 LICENSE，未充分反映脚本自己的许可。其反查词典现在直接读取上游 `flypydz.dict.yaml`，主码表脚本仍使用反编译工具。本轮只读检查，没有执行反编译；脚本的许可也不自动覆盖官方词库数据。

libre-flypy 的代码采用 AGPL，发布码表另有 CC0 声明。其上游构建要求另外取得 IDS 与拼音输入，未锁定这些外部仓库版本；校验脚本还需要未随仓库提供的参考文件。因此，能运行生成器与完整可复现验证不能视为一回事。Babble 现有的锁定输入、轨迹和校验流程是本项目补充的工程措施。

## 为什么优先评估 Chai

[拆分配置文档](https://docs.chaifen.app/tutorial/analysis/)明确将小鹤列为“相交不拆”的适用方案。源码存在 `analysis.degenerator.no_cross`，实际利用笔画拓扑排除被其他笔画穿过的字根；还支持字根认同、笔画归并、规则优先级和自定义部件分析。

[字库结构](https://docs.chaifen.app/development/data/)区分含矢量笔画的基本部件与具有笔顺关系的复合体；这种信息比单纯 IDS 的首末叶子更适合判断取形限制。[码表生成](https://docs.chaifen.app/tutorial/encode/)与[校对](https://docs.chaifen.app/tutorial/debug/)提供从元素序列到编码、再与现有码表核对的工作流。分析结果可成为 Babble JSON 导出器的输入，不必引入其整套网页界面。

检查的版本为 `f5a8c42fe93adc218014d22499f18d62449d5fc2`，程序 GPL-3.0-only，含独立 `packages/hanzi-chai` 算法包、20 个 YAML 示例及测试。该版本示例未找到完整小鹤配置，也未找到专门的小鹤分析器；相交选项并不自动覆盖小字衍生、插隔、廴辶优先等全部要求。

远程字形库由[获取脚本](https://github.com/hanzi-chai/hanzi-chai.github.io/blob/f5a8c42fe93adc218014d22499f18d62449d5fc2/scripts/fetch.ts)单独下载。本轮未找到明确覆盖该远程数据的独立许可说明，因此尚未将其纳入 Babble。代码的 GPL 声明不作为远程数据许可的代替。

另一个项目 [libchai](https://github.com/hanzi-chai/libchai) 是 Rust 编码、评测与布局优化库 / CLI，接受已有元素序列表。它与网页算法包的职责不同，不应将其描述成现成的字形解释数据库。旧 Python `pychai` 已归档，不作为本次首选路线。

## 对现有 Babble 的检查

当前 8,143 个可训练字是本项目的核验子集，不是对官方主库的完整复刻。使用已有、留在项目外的固定官方研究参照检查，`HY.txt` 的 632 个不同汉字、1,840 次汉字出现均有官方参照记录；当前剩余 24 字 / 82 次缺失属于本项目尚未建立通过核验的取形解释。

另以 Unihan `kTGHZ2013` 来源形成的 8,105 字代理集合检查：当前覆盖 7,895 字（97.41%），缺 210 字，另有 248 个可训练字在此代理集合之外。该集合尚未独立核对为完整官方字单，所以这不是正式的“官方字库覆盖率”；但它说明总字数超过 8,105 仍可能漏掉规范字。

建议后续以以下步骤验收：

1. 固定官方版本与可核对的规范字清单，分别统计不同字、读音、完整编码及解释覆盖。
2. 先确认 Chai 所需底层数据的使用条款，再用当前缺失的 24 字做独立配置试验；逐字核对首末根、编码与可解释的规则过程。
3. 验证通过后导出构建期 JSON，保留单字修订及回归集，再扩展到整份规范字清单。运行中的按键反馈继续只查本地数据。

## 官方查形页作为增量校对来源

2026-10-26 对 [官方查形页](https://flypy.cc/ix/) 的 HTML、页面脚本、样式及公开加载的 [ixdata.json](https://flypy.cc/ix/ixdata.json) 进行了只读检查。页面一次下载完整 JSON，查询随后在浏览器内存中进行；`?q=字` 是本地查询的深链参数，不是逐字服务器接口。

本轮取得的 JSON 为 665,857 字节、8,412 个汉字，SHA256 为 `6968764d45720778e5c9a462c2807cf5cf9acbb34f2cdc4585be6025de6b1db1`，与 Babble 已锁定的外部研究参照完全一致。HTTP 返回 `ETag: "6ad82774-a2901"`、`Last-Modified: Wed, 21 Oct 2026 02:46:12 GMT`。实际验证携带 `If-None-Match` 的条件请求得到 304、零正文。因此，更新方式可以是低频条件请求整份快照，再在本机逐字比较变化，无须逐字爬取。

页面脚本确认字段 `1` 为编码、`2` 为鹤形、`3` 为拆分、`4` 为拼音。解析时需注意：

- `-`、`+`、`*` 是用途标记，应与四码分别保存。
- 编码与拼音的排列不保证对应，必须按双拼前缀匹配；不能用数组下标直接配对。
- 部分根是命名部件或附带读音注记，不能假定每个根都是一个 Unicode 字符。页面样式没有显示为此依赖专用字根字体，换字体不能代替部件定义。
- 官方字段也需要结构验证，例如“蚓”的根字段含三个 token，不能自动截断或互换字段；拼音字段另有一条含私用区字符的异常记录。

与当前运行库的只读对照结果：

| 指标 | 数量 |
| --- | ---: |
| 官方参照不同汉字 | 8,412 |
| Babble 可训练不同汉字 | 8,143 |
| 当前编码 / 首末根与该快照不一致的条目 | 0 |
| 官方有记录、本项目尚未提供完整练习的字 | 269 |

0 冲突符合此前以同一快照筛选记录的设计，不是对所有读音、教学解释或官方数据本身的独立正确性保证。

269 个待补字分为：151 字缺少通过核验的来源推导；94 字涉及命名部件；23 字已有取形但现代 Unihan 读音未匹配代码；1 字的官方根字段结构异常。另有 201 个官方额外四码落在已知字上，却都没有匹配的现代来源读音前缀，不能自动视为漏掉的训练答案。

默认文章的 24 个缺字全部在官方快照内，其中 14 字缺少可采用的来源推导，10 字涉及命名部件。这使它们成为 Chai 配置试验的明确样本。

建议的增量流程分为两条链：

1. **官方快照链**：保存 URL、获取时间、SHA256、ETag、Last-Modified 和解析器版本，分别比较新增、删除、编码、根、读音及标记变化。
2. **教学资料链**：Chai 或其他明确来源产生根、路径和说明；与官方快照比较，将部件待定义、读音政策差异和参考异常分别交给复核，通过后纳入正式库。

官方数据的用途仍需与公开分发分开判断。本轮未发现明确覆盖该 JSON 的开放数据许可证；`robots.txt` 返回 404 也不是数据再分发许可。原始快照与包含官方字段的详细差异继续保留在项目外，不改变现有公开库的来源声明。本轮完成了实际抓取和差异分析，尚未将自动更新或原始官方资料接入产品。

## 可复查的构建入口

以下命令来自上游说明，分别在对应项目中使用。本轮未执行整套生成，也未替换当前数据源。

Chai：

```bash
# Chai 网页与独立算法包所在仓库
git clone https://github.com/hanzi-chai/hanzi-chai.github.io.git
cd hanzi-chai.github.io
bun install && bun run fetch
bun run dev
```

libre-flypy：在其仓库中，先按上游说明准备 IDS、拼音输入与校验数据，再执行：

```bash
cargo run --release
python rate.py
```

cubercsl/rime-flypy：在其仓库中，准备现有码表及编译工具后执行：

```bash
make dict
make -C fcitx5
```

Chai 的入口见[源码 README](https://github.com/hanzi-chai/hanzi-chai.github.io/blob/f5a8c42fe93adc218014d22499f18d62449d5fc2/README.md)；cubercsl 的 `make dict` 调用 Rime 编译器，见[固定 Makefile](https://github.com/cubercsl/rime-flypy/blob/9ee464765e325dfd4b04926028d79d60882e653e/Makefile)。这些步骤编译或生成其各自的数据，不能仅凭命令运行成功就证明整份小鹤教学解释正确。
