# 汉字覆盖扩展：常规四码与大字集拼字

日期：2026-10-28（Asia/Dubai）。用户已明确目标：**尽可能覆盖全部 Unicode 汉字，达到官方实际覆盖率**。8,143 个训练字、HY 的 95.54% 都不再作为覆盖完成标准。本轮重新核查官方机制、实读社区资料，并运行独立大字集原型；正式训练库尚未改变。

## 这次查明的根本问题

现有字库并非只有八千字。项目已经持有明确 CC0 的 libre-flypy 发布码表，实际有 **41,279 个不同字、49,854 个去重字码对**。当前 8,143 字是全码、现代读音和可解释首末根同时通过的子集。将解释资料不足一并处理成“不可练这个字”，挡住了已有可靠编码的常用字。

另一个限制是参照范围：当前官方查形 JSON 有 8,410 字。把它当成唯一准入白名单，无法覆盖官方的另一条大字集通道。官方采用的是**规范字主体与少量表外字的常规音形码，加上 OK 部件拼字**。[官方概述](https://flypy.cc/help/#/xh)、[Windows 说明第八节](https://flypy.cc/help/#/pc)明确区分两种输入；后者是 `ok` 加两至三个部件的双拼，通常为 6／8 键，不是所有字都有常规四码。

因此下一轮应同时推进常规四码补齐和大字集拼字，分别保存编码、字根证据和教学范围。不能为了扩大数字，把普通部件、社区生成码或本字没有的普通话读音伪装成已核验官方四码。

## 常规四码：可立即推进的候选

当前官方查形中的 269 个本地缺字，可以分流为：

| 分流 | 字数 | 下一步 |
| --- | ---: | --- |
| CC0 发布全码＋现有现代读音＋官方全码一致 | **158** | 建立“编码已核对、取形解释待补”的独立层，不等待完整教学才允许表达编码可用。按每个读音／全码对核验。 |
| 有现代音匹配的官方全码，但现有发布码不同或缺失 | 49 | 从许可结构、笔画与具体规则独立推导，或采用另一条明确来源，不能直接拷答案充当推导。 |
| 官方编码前缀未匹配现有现代读音 | 62 | 单独审查读音来源；其中 23 字已有取形轨迹，不能误当全部缺字形资料。 |

158 字中包括 HY 缺字里的走、现、声、其、带、延、欺、背、举、即、蝉、蠢、视、觉、途，共 55 次出现。分级接入后，HY 可由 1,758／1,840 提至 **1,813／1,840＝98.53%**；这是尚未实施的可达值。通规可达 8,048／8,105，仍有 57 字需要继续处理。

其余 HY 九字是无、生、大、见、平、升、夜、断、继。它们已有发布码，但旧形码与当前参照不一致，不应盲导。**平**已在项目外完成独立推导探针：许可 `Strokes.txt:244` 的五笔事实，结合[官方插入规则的同字例子](https://flypy.cc/help/#/gz)，原创记录首笔一与末部十的范围；使用已有一 A／十 U 映射和现代读音生成 PKAU，随后才与官方码及根比较，均一致。正式接入应新增独立策划层，保留旧生成物和来源锁，而非改旧参考来掩盖差异。

命名部件也不是永久阻塞。应给“见下、其上、具上”等稳定 component ID、明确笔画或几何范围及位置用法；允许非单个 Unicode 字符的部件对象，不能把“见下”随意换成儿。当前 94 个命名根缺字集中在少量重复部件，适合系统补定义。

现有 CC0＋现代读音候选有 41,261 字。与官方查形相交的 8,377 字中，8,118 字至少一码吻合，259 字没有匹配码；该交集的 96.91% 不能外推成长尾准确率，也不能证明每个读音／全码都正确。其余不在参照里的约 3.3 万候选应保留独立来源和未核对身份，不能简单全部默认开放为官方答案。

同一固定 Unihan 的其他读音属性可为上述 62 字中的 30 字提供有出处的匹配音，其中 19 字已有形轨迹；但 `kHanyuPinyin`／`kXHC1983` 包含旧字典、罕见或地区读音，须显式标注来源和用途，不覆盖当前默认现代音。

## 大字集：已实跑的近九万字部件拼字链

找到有明确数据来源说明的 [mirtlecn/rime-radical-pinyin 固定输入](https://github.com/mirtlecn/rime-radical-pinyin/blob/87e73d7182916f3db9dbc0b6a4d18a78a775b298/src/README.md)。`radical.yaml` 实读 98,483 个字键、120,315 个显式部件序列，包含大量增补平面字；上游逐项说明 GPLv3、CHISE IDS、chaizi 与 yi-bai IDS 的来源及条款。它是部件资料，不是官方鹤形答案。

固定文件为 1,663,188 B，SHA256 `c648dfd43a90f6ba60c123a7d57977cf8fc02dd470f2bee4e8fb2ef9343582b5`，commit `87e73d7182916f3db9dbc0b6a4d18a78a775b298`。现有 IDS 自身已有 97,091 个字键，新输入相对 IDS＋chaizi 并集净增 4,908 字键，不能宣传为净增十万；它的价值还包括大量替代部件序列。

独立原型使用源文件明确列出的 2／3 部件，以及现有 Unihan 和产品双拼算法。每个部件按固定来源顺序只选一个可编码读音，不枚举多音组合。另一个策略优先使用源程序显式列出的 78 个部件助记读音，仅读取 AST 字面量，不执行上游程序。**两个策略先完整生成候选，再读取官方挂接参照进行比较**，没有按答案调整拆分或选音。

| 原型结果 | 仅现代部件读音 | 加入上游部件助记读音 |
| --- | ---: | ---: |
| 可生成拼字的源字键 | 88,952 | 89,189 |
| 生成字码对 | 96,341 | 97,078 |
| 本字无现代音、部件仍可拼 | 46,618 | 46,804 |
| 与官方镜像参照至少一条拼字码相同的字 | 53,809 | **57,661** |

原型重复执行后两个候选包及汇总摘要一致。完整候选和含官方字段的比较仍只在项目外；可复跑工具见 [tools/coverage-research](../tools/coverage-research/README.md)。**89,189 是可生成的源字键数，不是已接入产品的字数、不是已核验官方覆盖，也不是九万字常规四码。**

### 差异原因的追加实测

独立 checker 指出官方公开规则另明确规定辶／廴用 `vi`、礻／衤用 `pp`。据此做了两项项目外后续试验，先按这四个整体规则生成、写出候选，之后才读取参照；没有加入逐字答案：

| 后续诊断策略 | 生成字键 | 生成码对 | 与参照至少一码完全相同的字 |
| --- | ---: | ---: | ---: |
| 助记音优先＋四部件整体规则 | 89,189 | 97,439 | **58,489** |
| 同上＋列出部件所有来源读音的有限组合 | 89,189 | 112,553 | **59,926** |

第二项为诊断，区别于初始两个不枚举策略；按不同双拼码去重，设每源行最多 256 组合，本次实际最大仅 12，未截断任何行。它证明首选读音政策会漏掉部分可核对组合；并不证明所有生成组合都被官方接受。独立复核重新从完整候选和原始参照算出同样数字，工程接入仍只能按每个字码对保留通过状态，不能一字有一条匹配就提升其全部候选。

两项后续试验是差异诊断，尚未并入下述便携工具的两个稳定基础策略；应在正式扩库生成器中将整体规则和读音候选政策明确版本化。与官方来源参照完全一致的 59,926 字仍未达到参照的 87,947 字覆盖，差异队列和缺失源拆法需要继续推进。

比较参照为 [rime-crane 的 OK 表](https://github.com/kchen0x/rime-crane/blob/71f3add6a39d58a8e8b35abc7ca9c998d766b274/xhup_dicts/xhup.ok.dict.yaml)，表头说明来自官方清风便携版 v1.26.9c。它有 88,020 行单字码对、**87,947 个不同字**，其中 60,378 个位于增补平面；SHA256 `510c6d7ab85b125d37a8b95cd1eb615371234aec353851f052e7a7a5ccf68d4a`。这是可检查的社区同步参照，尚未通过官方网站实际取得该明文原包，不能冒充本轮已完成官方原包溯源或获得整体重分发授权。

HY 原缺 24 字中，两个策略均生成 23 字／81 次；但 exact 比较分别只通过 7 字／30 次、12 字／46 次。夜的源行是四部件，被本轮 2／3 部件限制排除。因此不能用拼字原型宣称 HY 已经补齐；四码修复和拼字后备应分别继续。

## 官方覆盖、个人导入与开源生成分别推进

[官方挂接指导](https://flypy.cc/help/#/gj)明确给出百度安卓版个性短语 INI 及转换流程，格式为 `编码=序号,词条`；[用户词库说明](https://flypy.cc/help/#/yh)也有 TXT 导入导出。这提供了用户本机明文库接入的实际路径。应支持单字、词语、常规四码和 OK 拼字的受控分流，保留来源，不能从四码倒推根。

[官方应用说明](https://flypy.cc/help/#/yy)同时区分个人挂接与第三方内置。产品开源码与自带许可数据是一层，用户本地选择的官方明文库是另一层；后者不上传、不随源码包分发，也不自动变成有拆分解释的教学资料。下载可用和开源可重分发不是同一件事。

本轮实际尝试官方共享下载入口：永硕公开共享密码登录成功，但页面未加载文件列表；123 盘返回拒绝访问；清风公开方案市场的小鹤搜索返回空数组。没有取得原包，没有反编译 BIN。该限制不妨碍继续开发通用明文导入器，也不妨碍使用已许可部件资料独立生成扩展。

官方说拼字支持 GB 18030-2022。[教育部发布说明](https://www.moe.gov.cn/jyb_zzjg/huodong/202207/t20220729_649675.html)给出原发布版 87,887 汉字；[国家标准详情](https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=A1931A578FE14957104988029B0833D3)另有第 1 号修改单。支持声明、社区表 87,947 字与 Unicode 十万余字不是可互换数字；应比较实际字符集合与输入能力并集，不能简单相加。

## 交给工程的完整链路与验收

```text
固定 Unicode 目标集合／规范字／GB／Big5／用户文章
                     ↓ 分母、版本和缺口明确
许可发布四码 ──→ 字码对证据 ──→ 已核对编码可查／可练
许可结构／笔画 → 位置部件定义 → 首末形解释 → 逐字教学
许可部件序列 ─→ 部件读音与双拼 → 6／8 位独立拼字 → 官方参照后验比较
用户本机明文 ─→ 本地私有覆盖层 ─────────────────────┘
                     ↓
覆盖按维度报告、冲突保留、旧训练回归、源码与数据通知
```

| 阶段 | 可验收端点 |
| --- | --- |
| 1：拆开资格模型 | `codeEvidence`、`shapeEvidence`、`teachingEvidence`、`componentSpelling` 独立。旧 8,143 字的码、排序、课程及掌握记录保持。编码已通过而解释待补时如实显示；形码专项课只选有对应证据的字。 |
| 2：常用字实补 | 先生成并核验上述 158 个字的通过码对，补平及其他有限策划字；追清通规剩余 57 字及 HY 九字，不以 98.53% 作为完成。命名部件补稳定 ID、范围和位置依据；备选读音单独标注。 |
| 3：拼字后备 | 对近九万候选先完成 Unicode 目标相交、部件助记／拆法差异队列，正式区分参照一致与独立扩展。增加 6／8 键输入链，保留原四码训练；没有本字普通话读音也能解释“拼的是这些部件”。 |
| 4：对齐实际官方能力 | 加入用户本机明文库与格式校验，按官方四码＋拼字并集比较。记录官方参照外、源缺拆法、无部件读音和缺字形各类，不把未取得的原包假作已审计。 |
| 5：向全部 Unicode 推进 | 固定统一字／兼容字／变体的口径，逐批处理参照外长尾；原型生成只是候选，必须经过规则和来源审查。字体、查询、编码、解释、可练覆盖分别验收。 |

当前的工程优先级应继续是覆盖扩展，细节打磨不替代它。本轮研究证明了比八千字更广的可执行路径，但尚未达到用户的覆盖目标，也没有把研究原型误报成产品已扩库。
