# 大字集覆盖调研的独立复查

日期：2026-10-28（Asia/Dubai）。独立 checker 未参与调研原型或产品实现；本次仅复查证据与统计并撰写本文。用户的目标是尽可能覆盖 Unicode 汉字、达到官方实际覆盖，当前 8,143 字和 HY 95.54% 均不视为目标完成。

## 结论

**研究 Go：可以按工程交接推进产品分层扩库。** 已复核关键事实、集合统计、固定来源、原型生成顺序及正式研究工具，未发现阻塞问题。它证明存在近九万字的部件拼字候选链，**没有证明近九万字都是官方兼容四码，也没有增加产品当前训练字数**。本结论只允许进入工程，不表示用户覆盖目标已经达成。

## 独立执行的核对

checker 用 Vite SSR 加载当前真实 `TRAINING_ENTRIES`，得到 8,143 个不同字；再以 Python 独立遍历固定 Unihan 17.0.0 ZIP 的 `kTGH`、`kGB0`、`kBigFive`，没有直接采用另一代理生成的字集作为真值。

| 固定集合 | 字数 | 本次独立重算的当前可训练字 |
| --- | ---: | ---: |
| 通规一级 | 3,500 | 3,402 |
| 通规二级 | 3,000 | 2,939 |
| 通规三级 | 1,605 | 1,554 |
| 通规全部 | 8,105 | 7,895 |
| GB2312 `kGB0` | 6,763 | 6,497 |
| Big5 `kBigFive` | 13,064 | 5,156 |

因此通规一级缺 98 字、通规全部缺 210 字是实际集合差集，不能用“总训练字 8,143 超过 8,105”代替覆盖检查。

本 checker 另以 Python 从原型完整候选包和固定社区参照逐项重建 `字＋码` 集合，得到以下相同结果；不是只抄汇总文件：

| 原型策略 | 生成不同字键 | 生成码对 | 与固定 OK 参照完全相同的字 | 相同码对 |
| --- | ---: | ---: | ---: | ---: |
| 仅现代读音 | 88,952 | 96,341 | 53,809 | 53,813 |
| 上游部件助记读音优先 | 89,189 | 97,078 | 57,661 | 57,665 |

参照重新解析为 87,947 字／88,020 码对。后续目标审计确认这些候选及参照全部属于固定 Unihan 17／18 的记录，PUA 为 0；但不能据此把 Unihan 与 `Unified_Ideograph` 属性混作同一分母。

本 checker 另独立下载并解析 Unicode 17 `PropList.txt`，SHA256 `130dcddcaadaf071008bdfce1e7743e04fdfbc910886f017d9f9ac931d8c64dd`。`Unified_Ideograph` 有 101,996 字，含 12 个位于兼容区的属性例外；两种原型与其交集分别为 88,951／89,188，均有一个兼容字 U+2F8BD 不属于该属性。参照交集为 87,946，属性外兼容字为 U+F92E。另一个独立目标审计代理对 Unicode 18 同一属性实算为 101,997，原型及参照交集不变。主报告分别给出版本、分母和交集，没有用源字键总量直接冒充全 Unicode 覆盖率。

还验证了 10 份实际取得的官方 Markdown 与其清单 SHA256 相符；以 Python AST `literal_eval` 独立读取上游 `custom_dict`，78 项与原型采用的助记 JSON 完全相同，没有执行第三方生成脚本。检查脚本与本机原始证据保留在项目外 `/root/.cache/babble-coverage-research/checker/`，主要结果为 `independent-recheck.json`。

## 来源、生成与比较的边界

已逐行检查原型：两个策略都先由 radical 的显式 2／3 部件行、固定读音和产品 `explainSound` 生成全部候选并写出；之后才读取官方来源的社区 OK 镜像。参照没有决定部件拆法、部件选读或候选保留，没有用逐字答案调参。每个部件只按既定策略取第一个可编码读音，不枚举多音笛卡尔积。部件助记优先策略不能被称为现代标准读音策略。

还检查了主代理的两项后续差异诊断：四个整体读法直接来自官方公开规则，单读版先生成 97,439 码对，独立重算与参照相同的字为 58,489；有限读音组合版为 112,553 码对、59,926 个字至少一码相同。两者仍在候选生成完成后才读取参照，没有加入逐字答案。后者明确属于诊断性多音组合，单行上限 256，本次实际最大为 12；不能把初始两策略“不枚举”的说明泛化给它。多一条匹配不证明同字其他候选全部正确，工程交接要求按字码对分别核对。

已读取固定 `mirtlecn/rime-radical-pinyin` 的 LICENSE 与 `src/README.md`：数据构建说明明确列出 GPLv3，以及 chaizi CC BY 3.0、CHISE IDS GPLv2 or later、Yi Bai IDS MIT 的输入出处。它是可以继续采用和保留相应通知的具体资料链，不应因涉及 GPL／CC BY 就被笼统列为“不可用”。普通部件序列仍不等同于小鹤首末根；未来数据分发须保留各层许可及改动说明，不能将生成物一律重新标为原创 MIT。

官方 `pc.md` 的 OK 节实际写明 `ok＋二分双拼`、不足时三分，形成通常为 6／8 键的拼字通道；还明确给出辶／廴与礻／衤的读法归类。这是整体规则事实，可以独立整理为可审查的生成政策；与按逐字官方答案反填候选不同。官方 `xh.md` 以 8,105 规范字为主体、另以 GB 18030-2022 拼字补充，没有承诺每个 Unicode 汉字都有常规四码。

官方 `gj.md` 确实提供用户挂接用明文 INI 及转换格式说明；`yy.md` 区分用户安装／挂接与未经授权的第三方内置。社区镜像可供本次外部校对，仓库总体 GPL 不自动构成原官方整库的重新授权。用户本地明文导入是可继续评估的产品路径，不能把该设计本身说成官方已授予 Babble 数据再分发许可。本次没有取得官方网盘内实际码表，也未反编译 BIN。

## 尚未完成的产品目标

- 当前产品仍为 8,143 个训练字／8,806 个读音与全码选项，HY 仍缺 24 字／82 次；158 字码可用分层和“平”的推导均是候选或项目外证明，尚未正式接入。
- 四码存在性、首末根证据、完整教学与 OK 拼字必须分别记录；不能为提高覆盖伪造解释，也不能因解释未齐就将可靠现成编码一并宣称不存在。
- 约九万生成候选中，尚有较多与固定 OK 参照不同的拆法／部件读音，exact 子集也仍属于部件拼字而非四码训练。
- Unicode 目标须固定版本、区分统一汉字／兼容字／特殊符号／变体序列，并按集合计算。字体可显示、存在普通话读音、可通过部件拼字和已核验四码是不同能力。
- 公开产品的大字集加载、输入界面、来源展示、学习计分及回归仍待工程实施；本轮调研通过不能替代这些验收。

## 正式研究工具与工程交接检查

已阅读最终 [覆盖调研](coverage-expansion-survey.md)、[工程交接](coverage-implementation-handoff.md)、`tools/coverage-research/run.mjs`、输入锁、README 和六项测试。工具拒绝固定输入变化，不执行上游 Python；本地音码算法除 `sound.ts` 外，其实际运行依赖 `dictionary.ts`、`encoding.ts` 也已锁定。项目内路径、符号链接及输入／输出重叠有明确拒绝，候选与参照原件只在项目外处理；输出保留 GPL、CC BY、来源说明及 Unicode／键位通知，程序 MIT 未被用来重授权资料。

本 checker 实际运行专项测试：**1 个文件／6 项通过**。并以新的项目外输出目录独立执行正式 CLI，退出 0；两份完整候选 JSON 与原先探针输出**逐字节相同**，两策略所有汇总字段也完全相同。正式工具 SHA256 为 `4424f95128588f0af25a5a15a4df6d7aea3ffd5ba707bf23a8204ca728a69f74`，输入锁 SHA256 为 `967e3009de91e98fd15ed9006592c457cbe1f06e092f5d3863f20cddcc65f64c`。证据保存在项目外 `checker/portable-final/`、`checker/portable-final-recheck.json`，追加规则独立复算为 `checker/rule-followup-recheck.json`。主代理另报告本轮完整 `npm test` 为 14 文件／143 项通过，此项与本 checker 专项执行区分记录。

工程交接已给出实际可执行的顺序：分开编码／端点／教学资格，接入有来源且逐码对比较通过的 158 字，再补平等有限策划；将 6／8 位拼字另建输入、解释、目标计分及加载链；用户明文作为本地覆盖层；按固定 Unicode 集合及实际官方能力并集持续重算。它规定旧四码资料、课程及记录不退化，并对参照不一致、参照外候选、失败重试、文件边界、分发及三引擎回归分别验收，没有用阶段1或近九万候选总数代替用户目标。

因此研究证据及交接已足以开始工程。产品阶段仍须由独立 checker 验收实际字库、页面及覆盖提升，本报告不提前给产品扩库或全 Unicode 目标 Go。
